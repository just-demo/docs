# OWASP Top 10 (2025)

Interview-prep cheat sheet. Source: https://owasp.org/Top10/2025/

| # | Vulnerability | Examples | Prevention | What it is |
| --- | --- | --- | --- | --- |
| A01 | **Broken Access Control** | • Unverified parameter tampering in an SQL lookup: `pstmt.setString(1, request.getParameter("acct"))` — attacker edits the URL to `https://example.com/app/accountInfo?acct=notmyacct` and reads another user's account since there's no ownership check.<br>• Forced browsing to an admin URL: comparing `https://example.com/app/getappInfo` vs `https://example.com/app/admin_getappInfo` — if either is reachable by an unauthenticated or non-admin user, that's the flaw.<br>• Access control enforced only in front-end JS blocks the browser from reaching `.../admin_getappInfo`, but `curl https://example.com/app/admin_getappInfo` bypasses it completely since nothing checks server-side. | • Deny by default for anything non-public; enforce checks server-side, never trust the client.<br>• Enforce record ownership instead of unrestricted CRUD.<br>• Minimize/centralize CORS config instead of ad-hoc per-endpoint.<br>• Disable directory listing; remove backup/metadata files from web roots.<br>• Rate-limit APIs to blunt automated probing.<br>• Invalidate sessions server-side on logout; use short-lived JWTs + refresh tokens.<br>• Log and alert on access-control failures.<br>• Cover access control with automated tests, not just manual review. | Users can perform actions or view data outside their intended permissions — via parameter tampering, privilege escalation, forced browsing, or missing server-side checks. Ranked #1, present in ~100% of tested apps. |
| A02 | **Security Misconfiguration** | • Sample apps with known flaws left on production servers; default admin accounts never had their credentials changed, so attackers log into the admin console with the defaults.<br>• Directory listing left enabled lets attackers enumerate files, download compiled classes, decompile them, and hunt for access-control bugs.<br>• Verbose error pages return full stack traces to users, exposing component versions and internals useful for further attacks.<br>• Cloud storage left at its default, overly permissive sharing settings exposes data to the public internet. | • Automate a repeatable hardening process for every environment.<br>• Ship minimal platforms — no unused features, samples, or docs in production.<br>• Review/update configs (including cloud storage permissions) as part of patch management.<br>• Segment architecture so a misconfiguration in one component/tenant doesn't cascade.<br>• Send security headers (CSP, HSTS, etc.) by default.<br>• Automate configuration verification; manually audit at least annually if not.<br>• Prefer identity federation and short-lived credentials over static embedded secrets. | Insecure defaults, unnecessary enabled features, unpatched systems, verbose errors, or missing security headers — anywhere from the app to the cloud platform underneath it. |
| A03 | **Software Supply Chain Failures** | • SolarWinds (2019): a trusted vendor was compromised with malware; the malicious update alone compromised ~18,000 organizations that upgraded.<br>• Bybit theft (2025, $1.5B): a supply-chain attack embedded in wallet software that only activated maliciously when the target wallet was actually being used.<br>• Shai-Hulud npm worm (2025): the first successful self-propagating npm worm — seeded malicious versions of popular packages with a post-install script that harvested and exfiltrated secrets to public GitHub repos, auto-detected any npm tokens on the victim's machine, and used them to push malicious versions of every package it could reach; spread to 500+ package versions before npm stopped it.<br>• Vulnerable components run with the app's own privileges, so a flaw in any one is high-impact: CVE-2017-5638 (Apache Struts 2 RCE) and CVE-2021-44228 "Log4Shell" (Apache Log4j RCE) are both blamed for major breaches, ransomware, and cryptomining campaigns. | • Maintain a Software Bill of Materials (SBOM) covering direct and transitive dependencies.<br>• Continuously monitor CVE feeds for components in use.<br>• Pull components only from official, trusted sources over secure connections.<br>• Enforce rigorous change management across CI/CD, repos, and dev tooling.<br>• Require separation of duties — no single person can push straight to production.<br>• Roll out patches via staged deployment rather than all-at-once.<br>• Harden supply-chain systems themselves with MFA, access controls, and signed artifacts. | Vulnerabilities or malicious changes introduced through third-party dependencies, tools, or vendors the application relies on, rather than first-party code. |
| A04 | **Cryptographic Failures** | • A site doesn't enforce TLS on every page / allows weak ciphers; an attacker on an insecure wireless network downgrades HTTPS to HTTP, steals the session cookie, and replays it to hijack the session — reading or modifying private data, or redirecting a money transfer.<br>• A password DB stores unsalted or simply-hashed passwords; a file-upload vulnerability lets the attacker exfiltrate it. Unsalted hashes fall to rainbow tables; even salted passwords can fall to GPU cracking if the hash function itself is fast/weak. | • Classify data by sensitivity; know what actually needs protecting.<br>• Store sensitive keys in an HSM (hardware or cloud-based).<br>• Use well-vetted crypto library implementations, not homegrown crypto.<br>• Minimize what sensitive data you store; discard promptly or tokenize (PCI DSS style).<br>• Encrypt sensitive data at rest with strong, current algorithms and proper key management.<br>• Encrypt data in transit: TLS 1.2+, forward secrecy, HSTS to force HTTPS.<br>• Disable caching of sensitive responses at CDN/server/app layers.<br>• Avoid unencrypted protocols for sensitive data (plain FTP, SMTP, etc.).<br>• Hash passwords with strong adaptive salted algorithms (Argon2, scrypt, PBKDF2-HMAC-SHA-512).<br>• Use cryptographically secure, non-reused IVs; prefer authenticated encryption.<br>• Generate keys with proper CSPRNGs; avoid predictable seeding.<br>• Avoid deprecated primitives: MD5, SHA1, CBC mode, PKCS#1 v1.5.<br>• Have security specialists review crypto configuration.<br>• Start planning for post-quantum crypto migration (target: by end of 2030). | Sensitive data exposed due to missing encryption, weak/outdated algorithms, poor key management, or flawed crypto implementation (bad IVs, deprecated hashes, padding oracles). |
| A05 | **Injection** | • SQL injection: `"SELECT * FROM accounts WHERE custID='" + request.getParameter("id") + "'"` with request `.../accountView?id=' OR '1'='1` turns the WHERE clause into a tautology and dumps every row instead of one customer's.<br>• ORM/HQL injection: the same pattern against a Hibernate query — `"FROM accounts WHERE custID='" + request.getParameter("id") + "'"` — payload `' OR custID IS NOT NULL OR custID='` dumps every account, showing ORMs aren't automatically safe if input is still concatenated in.<br>• OS command injection: `Runtime.getRuntime().exec("nslookup " + request.getParameter("domain"))` — payload `example.com; cat /etc/passwd` runs an arbitrary shell command appended after the `;`. | • Use safe/parameterized APIs, or an ORM, instead of building queries via string concatenation (note: stored procs that concatenate internally are still vulnerable).<br>• Apply positive (allow-list) server-side input validation — not sufficient alone, but a solid layer.<br>• Escape special characters for the target interpreter when dynamic queries can't be avoided (can't fully protect identifiers like table/column names).<br>• Bake SAST/DAST/IAST scanning into CI/CD to catch injection flaws before production. | Untrusted input is passed to an interpreter (SQL, OS shell, LDAP, ORM/HQL, expression languages) and executed as part of a command instead of being treated as plain data. |
| A06 | **Insecure Design** | • Credential recovery via security questions — prohibited by NIST 800-63b, OWASP ASVS, and the OWASP Top 10 itself, since answers aren't reliable identity evidence (more than one person can know them). The fix is removing the feature and redesigning recovery, not patching it.<br>• A cinema chain's group-booking flow caps a single booking at 15 seats before requiring a deposit — but nothing stops a scripted attacker from booking 600 seats across every cinema at once in a handful of requests, since the limit was never threat-modeled against automation.<br>• An e-commerce retailer with no anti-bot design lets scalper bots buy out all high-end video cards within seconds of stock going live, to resell at markup — hurting the manufacturer, the retailer's reputation, and real customers; countered by rules like flagging purchases completed within seconds of availability. | • Build a secure development lifecycle with AppSec involvement on security/privacy-sensitive features.<br>• Maintain a library of vetted, reusable secure design patterns and components.<br>• Threat-model authentication, access control, and other critical/business-logic flows.<br>• Bake security requirements into user stories from the start.<br>• Validate input/business rules at every application tier, not just the edge.<br>• Write tests (unit/integration) that explicitly validate against the threat model.<br>• Define both use-cases and misuse-cases per tier.<br>• Segregate system/network layers by exposure level; enforce tenant isolation. | Missing or ineffective security controls baked into the architecture itself — a flaw in the design, not the implementation. Perfect coding can't fix a control that was never designed in. |
| A07 | **Authentication Failures** | • Credential stuffing and "hybrid" password spraying: attackers try known username/password pairs and pattern-incremented guesses (e.g. `Winter2025` → `Winter2026`); without anti-automation defenses, the login endpoint becomes a "password oracle" confirming which guesses are valid.<br>• Most authentication breaches trace back to password-only auth; mandatory rotation policies backfire by pushing users toward reused or weakened passwords — NIST 800-63 recommends dropping forced rotation and enforcing MFA on critical systems instead.<br>• Broken session timeout / no Single Logout on SSO: closing a browser tab without logging out leaves the session live; on SSO especially, a user may believe they've logged out of "the app" while every other federated app under that SSO session stays authenticated for whoever uses the machine next. | • Enforce MFA everywhere feasible.<br>• Encourage password managers; don't block long/random passwords.<br>• Never ship default credentials.<br>• Check new passwords against top-10k weak-password and known-breach lists.<br>• Follow NIST 800-63b guidance; don't force periodic rotation without cause.<br>• Harden registration/recovery flows against account enumeration.<br>• Rate-limit/lock out failed logins, with logging and alerting.<br>• Use secure server-side session management with high-entropy random session IDs.<br>• Prefer established auth frameworks/libraries over rolling your own.<br>• Validate JWT claims fully — audience, issuer, scopes — not just the signature. | Weaknesses in login, credential storage, session, or MFA handling let an attacker be recognized as a legitimate user. Covers 36 CWEs; unchanged at #7 since 2021. |
| A08 | **Software or Data Integrity Failures** | • A support subdomain is mapped through an external provider such that the browser sends the main domain's cookies — including auth tokens — to that third party; anyone with access to the support provider's infrastructure can steal every user's cookies and hijack sessions.<br>• Router / set-top-box / IoT firmware ships without signed-update verification; unsigned firmware is "a growing target for attackers," with little fix beyond waiting for vulnerable versions to age out.<br>• A developer pulls a package from an unofficial website instead of a trusted registry; with no cryptographic signature there's no way to verify integrity, and the package turns out to include malicious code.<br>• A React front-end exchanges serialized user state with Spring Boot microservices; an attacker recognizes the `rO0` (base64-encoded Java-object) signature, runs it through a Java Deserialization Scanner, and achieves remote code execution on the server. | • Verify authenticity with digital signatures before trusting software/data.<br>• Pull dependencies only from trusted repositories (internal vetted mirrors for high-risk cases).<br>• Review code and config changes to catch malicious code before merge.<br>• Keep CI/CD pipelines segregated, properly configured, and access-controlled.<br>• Reject unsigned/unencrypted serialized data from untrusted clients; verify integrity before deserializing. | Code, CI/CD pipelines, or serialized data are trusted without verifying they weren't tampered with — missing signature checks, unverified auto-updates, insecure deserialization. |
| A09 | **Security Logging and Alerting Failures** | • A children's health plan had no monitoring or logging in place; an external party had to inform them that an attacker accessed and modified records for 3.5M+ children — the breach may have run since 2013, undetected for over 7 years.<br>• A major Indian airline exposed 10+ years of passenger data, including passport and credit card details, at a third-party cloud host — discovered only when the cloud provider eventually reported the compromise.<br>• A major European airline suffered a GDPR-reportable breach via vulnerabilities in its payment application, with 400,000+ customer payment records harvested; the regulator fined the airline £20 million. | • Log all security-relevant events consistently (logins, failed attempts, high-value transactions).<br>• Emit logs in formats compatible with standard log-management tooling.<br>• Encode log data properly to prevent log-injection attacks.<br>• Use append-only/integrity-protected audit trails.<br>• Define real monitoring/alerting use cases with response playbooks, not just raw log collection.<br>• Back up logs and protect them from tampering or deletion.<br>• Have an incident response plan aligned with a standard (e.g. NIST 800-61). | Without adequate logging, monitoring, and alerting, breaches go undetected and incident response is slow or nonexistent. |
| A10 | **Mishandling of Exceptional Conditions** | • Resource exhaustion (DoS): a file-upload handler catches exceptions but never releases the resources/locks it was holding when one occurs — each failed upload leaks a little more capacity until the app runs out and falls over.<br>• Sensitive data exposure: database errors are returned to the user with the full underlying error instead of a generic message; attackers deliberately trigger errors as reconnaissance to craft sharper follow-up attacks like SQL injection.<br>• Financial transaction compromise: a multi-step transaction (debit → credit → log) has no proper rollback; an attacker interrupts it mid-sequence (e.g. via network disruption), and the missing atomicity lets them drain an account or duplicate a transfer through the resulting race condition / incomplete error handling. | • Catch exceptions at their source and handle them meaningfully, not just swallow them.<br>• Fail closed: roll back incomplete transactions entirely rather than partial recovery.<br>• Centralize error handling for consistent behavior app-wide.<br>• Add rate limiting, resource quotas, and throttling to blunt resource-exhaustion attacks.<br>• Log and alert on repeated errors — they often indicate an attack in progress.<br>• Apply strict input validation plus a global exception handler as a last-resort fallback.<br>• Include failure-mode threat modeling in design/security reviews. | Applications fail to prevent, detect, or properly respond to unusual/error conditions — missing validation, poor exception handling, uncontrolled failure states. |
