# OWASP Top 10 (2025)

Interview-prep cheat sheet. Source: https://owasp.org/Top10/2025/

| # | Vulnerability | Examples | Prevention | What it is |
| --- | --- | --- | --- | --- |
| A01 | **Broken Access Control** | • Parameter tampering: `.../accountInfo?acct=notmyacct` — swapping an ID to view someone else's account.<br>• Forced browsing / URL guessing: hitting `.../admin_getappInfo` directly, hoping for no access check.<br>• Bypassing client-side-only restrictions with `curl` since the check never happens server-side.<br>• Privilege escalation, JWT tampering, CORS misconfiguration, missing checks on API methods (not just UI buttons). | • Deny by default for anything non-public; enforce checks server-side, never trust the client.<br>• Enforce record ownership instead of unrestricted CRUD.<br>• Minimize/centralize CORS config instead of ad-hoc per-endpoint.<br>• Disable directory listing; remove backup/metadata files from web roots.<br>• Rate-limit APIs to blunt automated probing.<br>• Invalidate sessions server-side on logout; use short-lived JWTs + refresh tokens.<br>• Log and alert on access-control failures.<br>• Cover access control with automated tests, not just manual review. | Users can perform actions or view data outside their intended permissions — via parameter tampering, privilege escalation, forced browsing, or missing server-side checks. Ranked #1, present in ~100% of tested apps. |
| A02 | **Security Misconfiguration** | • Leftover sample apps / default admin accounts with default credentials still active in production.<br>• Directory listing enabled, letting attackers enumerate files and decompile classes to find flaws.<br>• Verbose error pages exposing stack traces and library versions.<br>• Cloud storage buckets left at default "internet-accessible" permissions. | • Automate a repeatable hardening process for every environment.<br>• Ship minimal platforms — no unused features, samples, or docs in production.<br>• Review/update configs (including cloud storage permissions) as part of patch management.<br>• Segment architecture so a misconfiguration in one component/tenant doesn't cascade.<br>• Send security headers (CSP, HSTS, etc.) by default.<br>• Automate configuration verification; manually audit at least annually if not.<br>• Prefer identity federation and short-lived credentials over static embedded secrets. | Insecure defaults, unnecessary enabled features, unpatched systems, verbose errors, or missing security headers — anywhere from the app to the cloud platform underneath it. |
| A03 | **Software Supply Chain Failures** | • SolarWinds (2019): malicious updates from a trusted vendor infected ~18,000 organizations.<br>• Bybit crypto theft (2025, $1.5B): wallet software compromised via a supply-chain attack that only activated under specific conditions. | • Maintain a Software Bill of Materials (SBOM) covering direct and transitive dependencies.<br>• Continuously monitor CVE feeds for components in use.<br>• Pull components only from official, trusted sources over secure connections.<br>• Enforce rigorous change management across CI/CD, repos, and dev tooling.<br>• Require separation of duties — no single person can push straight to production.<br>• Roll out patches via staged deployment rather than all-at-once.<br>• Harden supply-chain systems themselves with MFA, access controls, and signed artifacts. | Vulnerabilities or malicious changes introduced through third-party dependencies, tools, or vendors the application relies on, rather than first-party code. |
| A04 | **Cryptographic Failures** | • Attacker on insecure WiFi downgrades HTTPS to HTTP, steals session cookies, hijacks the session.<br>• A leaked password database using unsalted or weak hashes gets cracked via rainbow tables / GPU brute force — even salted hashes fall if the hash function itself is weak. | • Classify data by sensitivity; know what actually needs protecting.<br>• Store sensitive keys in an HSM (hardware or cloud-based).<br>• Use well-vetted crypto library implementations, not homegrown crypto.<br>• Minimize what sensitive data you store; discard promptly or tokenize (PCI DSS style).<br>• Encrypt sensitive data at rest with strong, current algorithms and proper key management.<br>• Encrypt data in transit: TLS 1.2+, forward secrecy, HSTS to force HTTPS.<br>• Disable caching of sensitive responses at CDN/server/app layers.<br>• Avoid unencrypted protocols for sensitive data (plain FTP, SMTP, etc.).<br>• Hash passwords with strong adaptive salted algorithms (Argon2, scrypt, PBKDF2-HMAC-SHA-512).<br>• Use cryptographically secure, non-reused IVs; prefer authenticated encryption.<br>• Generate keys with proper CSPRNGs; avoid predictable seeding.<br>• Avoid deprecated primitives: MD5, SHA1, CBC mode, PKCS#1 v1.5.<br>• Have security specialists review crypto configuration.<br>• Start planning for post-quantum crypto migration (target: by end of 2030). | Sensitive data exposed due to missing encryption, weak/outdated algorithms, poor key management, or flawed crypto implementation (bad IVs, deprecated hashes, padding oracles). |
| A05 | **Injection** | • SQL injection: `"SELECT * FROM accounts WHERE custID='" + id + "'"` with input `' OR '1'='1` returns every row.<br>• ORM/HQL injection: same idea against Hibernate query strings — `' OR custID IS NOT NULL OR custID='` dumps all records.<br>• OS command injection: `"nslookup " + domain` with input `example.com; cat /etc/passwd` runs an arbitrary shell command. | • Use safe/parameterized APIs, or an ORM, instead of building queries via string concatenation (note: stored procs that concatenate internally are still vulnerable).<br>• Apply positive (allow-list) server-side input validation — not sufficient alone, but a solid layer.<br>• Escape special characters for the target interpreter when dynamic queries can't be avoided (can't fully protect identifiers like table/column names).<br>• Bake SAST/DAST/IAST scanning into CI/CD to catch injection flaws before production. | Untrusted input is passed to an interpreter (SQL, OS shell, LDAP, ORM/HQL, expression languages) and executed as part of a command instead of being treated as plain data. |
| A06 | **Insecure Design** | • Security questions used for account recovery — multiple people often know the same answers, violating NIST 800-63b.<br>• A cinema booking system with no business-logic limits lets an attacker reserve hundreds of seats across every venue.<br>• An e-commerce site with no bot protection gets its high-value stock bought out entirely by scalper bots. | • Build a secure development lifecycle with AppSec involvement on security/privacy-sensitive features.<br>• Maintain a library of vetted, reusable secure design patterns and components.<br>• Threat-model authentication, access control, and other critical/business-logic flows.<br>• Bake security requirements into user stories from the start.<br>• Validate input/business rules at every application tier, not just the edge.<br>• Write tests (unit/integration) that explicitly validate against the threat model.<br>• Define both use-cases and misuse-cases per tier.<br>• Segregate system/network layers by exposure level; enforce tenant isolation. | Missing or ineffective security controls baked into the architecture itself — a flaw in the design, not the implementation. Perfect coding can't fix a control that was never designed in. |
| A07 | **Authentication Failures** | • Credential stuffing / password spraying with breached username-password lists, sometimes pattern-incrementing guesses (e.g. `Winter2025` → `Winter2026`); an app without defenses becomes a "password oracle."<br>• Legacy policies (forced rotation, complexity rules) push users toward weak, reused passwords instead of following NIST 800-63 + MFA.<br>• No session timeout / no Single Logout on SSO — a shared/public computer or closed tab leaves the session (and every federated app) open to the next person. | • Enforce MFA everywhere feasible.<br>• Encourage password managers; don't block long/random passwords.<br>• Never ship default credentials.<br>• Check new passwords against top-10k weak-password and known-breach lists.<br>• Follow NIST 800-63b guidance; don't force periodic rotation without cause.<br>• Harden registration/recovery flows against account enumeration.<br>• Rate-limit/lock out failed logins, with logging and alerting.<br>• Use secure server-side session management with high-entropy random session IDs.<br>• Prefer established auth frameworks/libraries over rolling your own.<br>• Validate JWT claims fully — audience, issuer, scopes — not just the signature. | Weaknesses in login, credential storage, session, or MFA handling let an attacker be recognized as a legitimate user. Covers 36 CWEs; unchanged at #7 since 2021. |
| A08 | **Software or Data Integrity Failures** | • DNS mapped to an external support vendor inadvertently shares the main domain's auth cookies, enabling session hijacking.<br>• Router/IoT firmware updates ship unsigned, letting attackers push malicious firmware to every device.<br>• Developers pull packages from random websites instead of trusted package managers, risking injected malicious code.<br>• Deserializing untrusted user-controlled state (e.g. a Java object blob starting with `rO0` in base64) enables remote code execution. | • Verify authenticity with digital signatures before trusting software/data.<br>• Pull dependencies only from trusted repositories (internal vetted mirrors for high-risk cases).<br>• Review code and config changes to catch malicious code before merge.<br>• Keep CI/CD pipelines segregated, properly configured, and access-controlled.<br>• Reject unsigned/unencrypted serialized data from untrusted clients; verify integrity before deserializing. | Code, CI/CD pipelines, or serialized data are trusted without verifying they weren't tampered with — missing signature checks, unverified auto-updates, insecure deserialization. |
| A09 | **Security Logging and Alerting Failures** | • A health plan provider's breach of 3.5M children's records went undetected for over 7 years due to no monitoring.<br>• An Indian airline's decade of passenger data was breached at a third-party cloud provider — discovered only when the provider eventually reported it. | • Log all security-relevant events consistently (logins, failed attempts, high-value transactions).<br>• Emit logs in formats compatible with standard log-management tooling.<br>• Encode log data properly to prevent log-injection attacks.<br>• Use append-only/integrity-protected audit trails.<br>• Define real monitoring/alerting use cases with response playbooks, not just raw log collection.<br>• Back up logs and protect them from tampering or deletion.<br>• Have an incident response plan aligned with a standard (e.g. NIST 800-61). | Without adequate logging, monitoring, and alerting, breaches go undetected and incident response is slow or nonexistent. |
| A10 | **Mishandling of Exceptional Conditions** | • A file-upload handler catches the exception but never releases the lock it held, eventually exhausting resources (DoS).<br>• Raw database errors shown to users leak schema/internal details, helping attackers craft better injection payloads. | • Catch exceptions at their source and handle them meaningfully, not just swallow them.<br>• Fail closed: roll back incomplete transactions entirely rather than partial recovery.<br>• Centralize error handling for consistent behavior app-wide.<br>• Add rate limiting, resource quotas, and throttling to blunt resource-exhaustion attacks.<br>• Log and alert on repeated errors — they often indicate an attack in progress.<br>• Apply strict input validation plus a global exception handler as a last-resort fallback.<br>• Include failure-mode threat modeling in design/security reviews. | Applications fail to prevent, detect, or properly respond to unusual/error conditions — missing validation, poor exception handling, uncontrolled failure states. |
